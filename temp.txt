For a dashboard that depends on multiple heavy APIs, I separate server state from local UI state and avoid fetching everything at once. I usually use TanStack Query to manage API data because it gives me caching, deduplication, background refetching, retries and request cancellation. For dashboard sections, I fetch data in parallel rather than sequentially, and I use pagination or lazy loading for large datasets. I also keep expensive operations such as analytics and reporting on the backend, where the API can return aggregated data instead of sending millions of records to the frontend.On the frontend side, I split the dashboard into smaller components and use React Server Components where possible, so only interactive parts need client-side state. For repeated data, I use caching at both the frontend and backend levels, for example Redis on the backend. For real-time data, I use WebSockets selectively instead of polling everything.

I wouldn’t let the HTTP request wait indefinitely for the AI provider. First, I’d configure a reasonable timeout for the OpenAI API request using something like an AbortController or HTTP client timeout.
For operations that don’t need an immediate response, I’d move the AI processing to a background job queue, such as BullMQ with Redis. The API would immediately return a job ID, and the client could poll for the result or receive it through WebSocket. I’d also implement retry with exponential backoff for errors such as 429 or 500 responses, but I’d avoid retrying indefinitely. I’d also monitor latency, timeout rates, token usage, and failure rates using logging and metrics.
